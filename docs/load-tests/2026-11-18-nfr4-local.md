# NFR-4 load test, 18 November 2026: development laptop

**Result: NFR-4 met on this machine once chat events were gathered into frames (100 ms).** Before that, delivery missed its target, though nothing was lost.

**NFR-4:** one event, 500 concurrent attendees and 20 chat messages a second, on a single API instance.

**SLO** (docs/06, section 7): chat delivery 95% under 1 second. NFR-3 adds API reads under 300 ms at p95 at that load.

## What ran

`npm run load:nfr4` (`load/`), against the production-like stack (`npm run stack:up`), with one API instance and telemetry on.

1. **Seed:** `load/seed.mjs` writes one live public event and 500 verified attendees with sessions straight to the database.
2. **Attendees** (`load/k6/nfr4.js`):
   - 500 virtual attendees speak the real-time protocol (Socket.IO over WebSocket), connecting over the first minute.
   - Each joins the event's chat and sends a message every 25 seconds, staggered, so 20 a second in all, for 3 minutes.
   - Every attendee receives every message: 10,000 deliveries a second.
3. **Reads:** API reads run alongside: the event, the attendee's admission, the chat history and the questions.
4. **What is checked:**
   - every join and every send succeed;
   - no sequence number is skipped (nothing lost);
   - delivery time from send to receipt, at p95;
   - read time at p95.

k6 runs in the stack's network and talks to the API directly, each virtual attendee with an address of its own. The per-address limits are not what is measured.

**Machine:**

- Intel Core i9-9880H, 8 cores and 16 threads, a laptop.
- Docker Desktop 29.2.1, VM with 16 CPUs and 8 GB.
- k6 2.3.0, the stack, Grafana (otel-lgtm) and the API all share the machine.

## Reading those results

**Reliability holds.** Over five runs and 6.6 million deliveries:

- no message was lost or skipped;
- every send was acknowledged;
- every attendee connected and joined.

**Throughput does not.**

- The API delivers chat at close to, but under, the 10,000 deliveries a second the target needs. During the steady phase a backlog builds and latency grows with it:
  - after 1 minute, p95 is 0.67 s;
  - after 3 minutes, p95 is 3 s with the API on cores of its own.
- Reads wait behind the same event loop.
- The API's CPU sat between 120% and 190% during the steady phase: its main thread was saturated.

**Where the time goes.** A CPU profile of the API (`node --prof`, telemetry on) shows:

- **85% of its samples in libc (musl), mostly in `writev`,** called from `ws` writing one frame to each socket for each message (`engine.io` → `socket.io` broadcast). One message to 500 attendees is 500 writes, so 20 messages a second is 10,000 system calls a second on one thread.
- Database work is about 6%.
- OpenTelemetry's own functions are each well under 1%.

**This machine magnifies the cost.**

- With the API and k6 competing for the same cores, p95 was 11.6 s; with each pinned to cores of its own, 3.1 s.
- Inside Docker Desktop's virtual machine on a laptop, a system call costs far more than on a Linux server.
- The run with telemetry off (3.26 s) is within this machine's noise of the pinned run with telemetry on (3.11 s), so telemetry is not the cause.

## After the change: chat events in frames

The decision was to send fewer frames. The API gathers an event's chat events for up to 100 ms (`CHAT_BATCH_MS` in `apps/api/src/live/fanout.ts`) and sends them as one `chat.events` frame per connection. Order, sequence numbers and replay are unchanged (docs/04). Same runs, same machine, the stack rebuilt:

| Run                                                 | Reads           | Delivery p95 | Delivery median | Reads p95   | Messages lost  | Joins failed |
| --------------------------------------------------- | --------------- | ------------ | --------------- | ----------- | -------------- | ------------ |
| Target, API pinned to cores 0–3, k6 to cores 8–15   | 9 page loads/s  | **442 ms** ✓ | 98 ms           | **67 ms** ✓ | 0 of 1,700,000 | 0            |
| Target, `npm run load:nfr4` as it is (cores shared) | 9 page loads/s  | **566 ms** ✓ | 112 ms          | **94 ms** ✓ | 0 of 1,700,000 | 0            |
| Stress: 50 page loads/s (200 requests/s)            | 50 page loads/s | 1.75 s ✗     | 1.42 s          | 1.31 s ✗    | 0 of 1,700,000 | 0            |

- At the target load, every threshold passes, also with k6 competing for the same cores.
- The API's CPU dropped from 120–190% to 55–120% in the steady phase.
- The 100 ms window is paid back many times over: median delivery rose from 35 ms (one minute, no gathering) to about 100 ms, and p95 fell from seconds to under 600 ms.
- The stress run shows where this machine's limit lies: page loads at six times the assumed rate, alongside full chat.

## What follows

- NFR-4 is verified again on the AWS demo instance before the public demo (milestone 10), with the same command.
- If more headroom is needed there, the next step is cheaper frames: a faster WebSocket server under Socket.IO.

To run it again: `npm run stack:up`, then `npm run load:nfr4`. Use `ATTENDEES`, `SEND_EVERY_MS`, `READS_PER_SECOND`, `RAMP_S` and `STEADY_S` to change the load. The summary is in `load/out/summary.json`. The "Load test" workflow runs the same on a GitHub-hosted runner, on demand.
